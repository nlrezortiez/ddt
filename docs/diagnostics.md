# PR 1: диагностика и наблюдаемость

Этот этап не меняет критерий обнаружения, не записывает спектр на SD и не выносит
OLED в отдельный процесс. Запись/replay и изоляция I²C — следующие PR.
Новых Python-зависимостей и изменений EEPROM/firmware не требуется.

## Команды оператора

Из каталога релиза, без установки дополнительной команды:

```sh
.venv/bin/python3 -m ddt status
.venv/bin/python3 -m ddt status --json
.venv/bin/python3 -m ddt --version
```

После установки `deploy/ddt` в `/usr/local/bin/ddt` доступны сокращения:

```sh
ddt status
ddt status --json
ddt --version
```

Wrapper по умолчанию использует `/opt/ddt/current/.venv/bin/python3`. Для другого
размещения задать абсолютный `DDT_PROJECT_DIR` и, при необходимости, `DDT_PYTHON`.
Без аргументов wrapper показывает help, не начинает захват SDR.

`status` **только читает** JSON и `/proc`: не запускает runtime, не открывает SDR,
I²C/GPIO и не требует установленных аппаратных Python-библиотек. Для другого файла:

```sh
python3 -m ddt status --file build/status.json --json
```

Коды выхода:

| Код | Значение |
| --- | --- |
| 0 | Живой runtime, свежие данные SDR, все включённые в конфиге устройства готовы по последним операциям |
| 1 | Статус прочитан, но устройство не готово: остановка, устаревшие данные, нет SDR или отказ OLED/GPIO |
| 2 | Статуса нет, файл повреждён/недоступен или схема не поддерживается |

Предупреждения о потерях/покрытии не меняют код выхода автоматически. Они требуют
отдельной оценки: `ready` не означает полноценное покрытие спектра или обнаружение
дрона. Краткий текст — для человека; стабильный интерфейс для скриптов — JSON.

## Liveness и readiness

```sh
# Жив ли цикл управления (этот режим использует OpenRC):
.venv/bin/python3 -m ddt.health
# Есть ли свежие данные работающего SDR (не зависит от OLED):
.venv/bin/python3 -m ddt.health --ready
```

При отключённом HackRF первый возвращает 0, второй — 1. Так OpenRC не перезапускает
исправный цикл переподключения. При зависании самого runtime heartbeat устаревает
и проверка liveness перестаёт проходить. Файл статуса публикуется раз в секунду и
сразу при переходе состояния/изменении порога; стандартный предел возраста — 15 s.

CLI пересчитывает возраст статуса и последнего измерения **в момент чтения**.
Проверяются boot ID, PID и время создания процесса из `/proc/<pid>/stat`, включая
состояние zombie. Старый файл после перезагрузки или повторного использования PID
не становится зелёным. Измерения из replay никогда не дают live-readiness.

## Контракт JSON, schema_version = 2

В файле `/run/ddt/status.json` лежит snapshot. `ddt status --json` возвращает
`{"snapshot": ..., "assessment": ...}`, где assessment пересчитан при чтении.
При ошибке чтения возвращаются `error` и отрицательная assessment, без snapshot.

Основные поля:

| Поле | Смысл |
| --- | --- |
| `version.git_revision`, `git_dirty` | Commit и наличие локальных изменений, определяются один раз при старте; `null`, если Git недоступен |
| `version.source_sha256` | Хеш путей/содержимого `ddt/*.py`, `src/*.c`, `libhackrf/src/*.[ch]`, requirements; доступен без Git |
| `binary.path`, `binary.sha256` | Выбранный sweep и его хеш при старте; `null`, если файл недоступен; не заменяет manifest зависимостей |
| `boot_id`, `instance_id` | Идентификаторы загрузки ОС и отдельного запуска runtime |
| `configuration.id`, `values` | SHA256 канонического эффективного конфига и его значения после CLI overrides/кнопок |
| `startup_config_id` | Неизменный идентификатор конфига на старте |
| `first_measurement_after_seconds` | Время от создания runtime до поступления в очередь первого затем успешно разобранного измерения; `null` до него |
| `sdr` | PID, признак живого процесса, readiness, число попыток запуска, последний код завершения |
| `last_failure` | Последняя причина отказа SDR, время, PID и код выхода, если известен; сохраняется после восстановления |
| `transitions` | Последние 32 перехода: предыдущее/новое состояние, код причины, monotonic |
| `transition_count` | Общее число переходов текущего runtime |
| `hardware.display`, `hardware.gpio` | Включён ли компонент, готовность по последним операциям, ошибки, последняя ошибка/успех и длительность операций |
| `assessment.alive` | Свежий heartbeat живого runtime с совпавшей идентичностью процесса/загрузки |
| `assessment.ready` | Live SDR, состояние receiving, свежий последний валидный ряд |
| `assessment.device_ready` | `ready` плюс готовность всех включённых OLED/GPIO |

Старые верхнеуровневые поля `state`, `valid_rows`, `invalid_rows`, `restarts`,
`threshold_db`, `error`, `display_ready`, `gpio_ready` сохранены. `error` — текущая
ошибка, в отличие от исторической `last_failure`. `restarts` — запланированные
повторы приёмника внутри этого runtime, а не перезапуски Python через OpenRC.
При перезапуске Python счётчики обнуляются, меняется instance ID; история остаётся
в ротируемом логе. Один runtime не переносит счётчики из старого файла статуса.

Номер схемы 1/старый файл без номера отвергается новым CLI с кодом 2, а не
интерпретируется как исправный. После запуска нового релиза файл заменяется
атомарно. Для диагностики старого релиза при откате использовать его команды.

## Потери и производительность

`metrics` содержит:

- `received_rows`: полные строки stdout sweep, включая заголовки и невалидный CSV;
- `overflow_dropped_rows`: строки, реально вытесненные из заполненной очереди;
- `shutdown_discarded_rows`: оставшиеся необработанные строки при закрытии приёмника;
- `reader_errors`: ошибки чтения/слишком длинная или оборванная строка;
- `queue`: текущая глубина, ёмкость и максимальная заполненность за запуск;
- `received_rate`, `valid_rate`: скорости поступления строк и обработки валидных
  измерений. Окно около 5 s; фактическая длительность указана в `window_seconds`.

Эти счётчики накопительные в пределах instance ID и не теряются при переподключении
SDR. Ошибки CSV учитываются отдельно в `invalid_rows`. Это **не** счётчик потерянных
радиосэмплов USB. Неизвестные потери ниже stdout этим PR не измеряются.
В replay приёмник не создаётся: received/queue равны нулю, valid относится к файлу.

`timings` показывает count/last/mean/max в миллисекундах:

- `csv_processing`: разбор, детектирование и учёт покрытия; включая невалидные
  строки/заголовки, без ожидания очереди;
- `queue_latency`: от чтения полной строки до начала её обработки;
- `hardware_tick`: весь синхронный вызов аппаратного слоя;
- аппаратные `operation_duration`: OLED init/render/ошибочная попытка и GPIO
  init/poll соответственно. Неизменившийся кадр OLED не считается новой операцией.

Средние/максимумы — с начала runtime, не процентили. В памяти нет неограниченной
истории измерений. `null` значит «ещё не измерено», не нулевая задержка.
Зависший I²C-вызов пока не возвращает замер: об этом говорит устаревший heartbeat.
`display.ready` — успешная предыдущая инициализация/операция, не физическая проверка
свечения OLED; для неподвижного кадра новых I²C-операций может не быть.

## Наблюдаемое покрытие прохода спектра

`scan` не меняет детектор и ничего не отбрасывает из его входа. Для нашего CSV
граница оценивается по повторному появлению начальной частоты первого диапазона.
Между границами объединяются частотные интервалы валидных строк, обрезанные до
настроенных диапазонов. Дубли строк не повышают долю покрытия.

Есть счётчики полных/неполных наблюдаемых проходов, последняя доля покрытия,
длительность между граничными строками и время завершения. После подключения
сначала ожидается граница; EOF, рестарт, невалидный CSV и обнаруженное переполнение
очереди сбрасывают незавершённое наблюдение (`invalidated_scans`). Последний уже
закрытый проход сохраняется как исторический, его возраст нужно учитывать.

Ограничения:

- Используется порядок строк **нашего** sweep, не универсальный протокол SDR.
- Диапазоны, пересекающиеся после округления шага перестройки до 20 MHz, помечаются
  `supported=false`: границы неоднозначны. Детектирование при этом не выключается.
- Если граничная строка пропала до stdout и это не обнаружено, оценка может
  объединить несколько физических проходов. Без sequence ID от производителя
  нельзя доказать точное число проходов или отсутствие радиопотерь.
- Длительность измеряется по monotonic при чтении строк, не по времени RF-захвата.
  При replay это скорость обработки файла, не исходная длительность записи.
- Память интервалов ограничена; аномальная фрагментация сбрасывает наблюдение.

Следовательно, `scan.last_scan.complete=true` означает только полное **наблюдаемое
CSV-покрытие** в этом интервале, а не доказанную полноту приёма.

## Лог и причины переходов

Все сообщения нового runtime и stderr sweep получают boot ID, instance ID и
monotonic timestamp. Wall-clock остаётся для удобства; скачки NTP не меняют
таймауты, возраст статуса и длительности. Переходы логируются один раз, не на каждый
ряд. Изменение порога кнопками логирует старый/новый config ID; запись конфига на
SD при нажатии не производится.

Коды отказа: `receiver_exit`, `stdout_eof`, `reader_error`, `startup_timeout`,
`data_timeout`, `start_or_io_error`, `cleanup_timeout`. При восстановлении появляется
переход `valid_measurement`; последний отказ остаётся в status. Штатная остановка
имеет причину SIGTERM/SIGINT, replay — `replay_completed`/`replay_invalid`.

## Приёмка PR на Pi

1. Развернуть отдельный релиз обычным способом. Новый C-бинарник для этого PR не
   требуется по смыслу изменений, но сборка релиза по инструкции остаётся общей.
2. `ddt status --json`: версия соответствует релизу, config ID стабилен без
   изменений, alive/ready/device_ready — true, счётчики растут.
3. Изменить порог кнопкой: threshold и текущий config ID меняются, startup ID — нет.
4. Отключить SDR: alive остаётся true, ready становится false после обнаружения
   разрыва/таймаута. После подключения — true, last_failure и счётчики сохраняются.
5. Сравнить GPIO/OLED ошибки с реальными действиями. Провода I²C не отключать на
   включённом устройстве; для теста лучше отдельный конфиг с недоступным адресом.
6. После restart службы instance ID меняется; после загрузки ОС меняется boot ID.
7. На штатном диапазоне наблюдать complete/incomplete scan и потери, сравнить
   CPU/RSS/скорость обработки с предыдущим релизом. Не обещать нулевой overhead:
   новые измерения и учёт покрытия также требуют CPU.

Локальные автоматические тесты проверяют контракт и отказные сценарии, но не
подменяют проверку реального SDR, OLED и стоимости инструментирования на Pi.
