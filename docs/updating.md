# Обновление существующей установки одной командой

После первой миграции из [operations.md](operations.md) обычное обновление:

```sh
update_ddt ПОЛНЫЙ_SHA_КОММИТА
```

Это **идентификатор Git-коммита**, обычно 40 шестнадцатеричных символов, не SHA256
файла. Ветки, теги и сокращённые SHA намеренно не принимаются. Нужный коммит
должен быть закоммичен, опубликован и доступен Raspberry. Проверенный код и тесты
собираются/исполняются от root: используйте только доверенный репозиторий и
отревьюенные коммиты. SHA фиксирует содержимое, но сам по себе не удостоверяет автора.

## Однократная установка команды

На Raspberry от root. Сначала опубликовать коммит, содержащий updater.
`/root/ddt` здесь — исходный Git-репозиторий, **не работающий релиз**.

```sh
DDT_REV='ПОЛНЫЙ_SHA_КОММИТА_С_UPDATER'
git -C /root/ddt fetch origin
git -C /root/ddt show --no-patch --oneline "$DDT_REV"
DDT_BOOTSTRAP=$(mktemp -d /tmp/ddt-updater.XXXXXX)

git -C /root/ddt show "${DDT_REV}:scripts/update_ddt.py" > "$DDT_BOOTSTRAP/update_ddt" &&
    python3 "$DDT_BOOTSTRAP/update_ddt" --help &&
    install -m 0755 "$DDT_BOOTSTRAP/update_ddt" /usr/local/sbin/update_ddt
```

Если `/usr/local/sbin/update_ddt` уже существует, сначала проверить, что это именно
наш updater, и сохранить копию. Чужую команду не перезаписывать. updater —
один самостоятельный файл, использующий системный Python и стандартную библиотеку;
он не зависит от переключаемого venv и не обновляет сам себя автоматически.
Для новой версии updater повторить этот шаг с проверенным коммитом, **не во
время выполняющегося обновления**. Временный bootstrap-каталог можно сохранить.

## Требования и обычный запуск

- Существующая рабочая установка `/opt/ddt/current` → `/opt/ddt/releases/...`,
  OpenRC `sweep` и status schema 2 с диагностикой. updater не делает первую миграцию.
- Штатные файлы службы и конфигурации OpenRC из репозитория. Проверяется точное
  совпадение; локальные изменения, даже комментариев, требуют ручной проверки.
- Исправные включённые SDR/OLED/GPIO, готовое устройство перед обновлением.
- Не менее 1 GiB свободного места — это начальный барьер, не гарантия достаточности
  места для любого будущего релиза. Python, pip/venv и инструменты сборки из
  operations.md уже установлены. Системные пакеты должны быть исправны.
- Интернет для Git/Python-зависимостей и настроенный доступ к Git remote от root
  без интерактивного ввода. Сам runtime интернета не требует.
- На время операции стенд закреплён за одним оператором: не менять `current`,
  конфигурацию и службу вручную, не перезагружать и не выключать питание.

```sh
update_ddt ПОЛНЫЙ_SHA_НОВОГО_КОММИТА
```

По умолчанию URL берётся из `origin` репозитория `/root/ddt`, но исходники
скачиваются **непосредственно из этого remote**. Делать `git pull` на Raspberry
перед каждым обновлением не нужно. Можно явно задать доверенный источник:

```sh
update_ddt ПОЛНЫЙ_SHA --repo git@your-git-host:team/ddt.git
```

Допустим и локальный Git-репозиторий через `--repo /root/ddt`; в таком случае
нужный коммит должен уже присутствовать в нём. Незакоммиченные файлы не переносятся.
Используйте SSH-ключи/credential helper, не помещайте токен в URL.

## Что автоматизировано

1. Блокировка второго обновления, проверка действующей установки и её готовности,
   backup конфигурации и файлов службы, сохранение предыдущего пути.
2. Отдельный уникальный каталог `/opt/ddt/releases/<SHA>-<suffix>` на каждую попытку.
   Проверка точного коммита, новый venv по окончательному пути, закреплённые
   зависимости, wheelhouse, импорты аппаратных библиотек, сборка C.
3. Проверка действующего JSON, `make check` с новым C-бинарником, headless replay,
   сохранение manifest, pip freeze и SHA256 wheels. Старый сервис ещё работает.
4. Повторная проверка конфигурации/ссылки и готовности старого runtime. Только затем
   остановка службы, проверка отсутствия старых runtime/sweep, атомарное переключение
   ссылки и запуск нового релиза.
5. До 60 секунд ожидания: свежий статус именно нового коммита из нового каталога,
   готовые SDR и включённые OLED/GPIO. Нужны 10 секунд стабильного instance/restart
   counter и рост числа измерений. Одна запись `started` не является успехом.
6. При ошибке после начала остановки — остановка текущего релиза, возврат ссылки,
   запуск и такая же проверка старого. Если остановка или откат не удались,
   выводится явная ошибка; параллельный запуск второго приёмника не производится.

Повтор команды с уже работающим чистым и готовым SHA не пересобирает релиз.
Код завершения 0 означает успех/уже установленную версию, 1 — ошибку, **включая
успешный автоматический откат**, 2 — неверные аргументы/отсутствие root.

Конфигурация `/etc/ddt/detector.json`, init/conf OpenRC, ОС, EEPROM и firmware
не обновляются. Пользовательский `sweep_binary`, отличающийся от новой сборки
`build/bin/sweep`, отвергается. Если PR меняет контракт службы или требует миграции
конфигурации, необходим отдельный ручной план. Не форсируйте обход этих проверок.
Порог, изменённый кнопками только в памяти, как и при обычном рестарте, сбросится
к значению из JSON.

Зависимости пока собираются через сеть на каждой новой попытке. Версии закреплены,
но это не побитовая воспроизводимость всей ОС. Сохраняемые wheelhouse/manifest
служат основой для последующего offline/artifact-based deployment.

## Журналы, SSH и аварийное восстановление

В начале выводится каталог `/opt/ddt/updates/<SHA-prefix>-<suffix>` с файлами:

- `update.log`: полный вывод команд сборки и тестов;
- `transaction.json`: фаза, старый и новый релизы;
- `previous-release`, `detector.json`, `sweep.init`, `sweep.conf`: данные отката;
- `manifest.txt`: состав успешно подготовленной сборки.

Из второго SSH-сеанса можно смотреть `tail -f /opt/ddt/updates/ТОЧНЫЙ_КАТАЛОГ/update.log`.
Проверки готовности во время старта могут оставлять в логе временные ошибки статуса.
Итог операции определяется финальной фазой и кодом завершения, не отдельным traceback.
Перед передачей журналов проверить их на адреса remote и другие приватные данные.

Обычный Ctrl+C/SIGTERM/SIGHUP до переключения оставляет старый сервис работающим;
во время переключения вызывает попытку отката. Для устойчивости к разрыву SSH лучше
запускать из уже установленного `tmux`/`screen` или, указав полный SHA, через nohup:

```sh
DDT_OUTPUT=$(mktemp /tmp/ddt-update-output.XXXXXX)
nohup /usr/local/sbin/update_ddt ПОЛНЫЙ_SHA > "$DDT_OUTPUT" 2>&1 < /dev/null &
printf 'PID=%s, output=%s\n' "$!" "$DDT_OUTPUT"
```

`nohup` выводит итог в файл; дополнительно проверить `transaction.json`, текущую
ссылку и `ddt status`. Сборка ограничена 15 минутами на команду; команды службы —
30 секундами. updater не является отдельным OpenRC-сервисом.

**SIGKILL, потеря питания, повреждённая SD или зависший kernel I/O не позволяют
гарантировать автоматический откат.** После такого события сначала проверить
`transaction.json`, `readlink -f /opt/ddt/current`, процессы и `rc-service sweep status`.
Не удалять lock-файл для «разблокировки»: flock освобождается ядром при выходе процесса.
Каталог неудачной сборки и предыдущие релизы автоматически не удаляются.

Для ручного возврата выбрать **точный** каталог этой операции:

```sh
DDT_BACKUP='/opt/ddt/updates/ТОЧНЫЙ_КАТАЛОГ'
DDT_PREVIOUS=$(cat "$DDT_BACKUP/previous-release")
ls -ld "$DDT_PREVIOUS"
rc-service sweep stop
ps -ef | grep -E '[p]ython.*-m ddt|[b]in/sweep'
```

Если stop завершился ошибкой или процессы остались — **не продолжать**, исследовать
конкретные PID. Если всё остановлено, проверить, что current — ссылка, и переключить:

```sh
ls -ld /opt/ddt/current
DDT_SWITCH=$(mktemp -d /opt/ddt/rollback.XXXXXX)
ln -s "$DDT_PREVIOUS" "$DDT_SWITCH/current" &&
    mv -Tf "$DDT_SWITCH/current" /opt/ddt/current
rmdir "$DDT_SWITCH"
cd /opt/ddt/current
rc-service sweep start
sleep 5
.venv/bin/python3 -m ddt status
```

JSON/init/conf updater не менял, поэтому копировать backup поверх текущих файлов
без отдельной причины не надо. Перед продолжением после ошибки/прерывания изучить
журнал; новая попытка создаст другой каталог, не переиспользуя частично собранный venv.

## Приёмка на Raspberry

Тесты updater используют временные каталоги и подменённую службу: локальный CI
не доказывает работу OpenRC/USB на Pi. Первый запуск провести при физическом доступе.
Проверить успешное обновление, повтор того же SHA, отказ неизвестного SHA без
остановки работающего сервиса и запрет параллельного обновления. Откат после
неготовности/ошибки запуска проверять на стенде с сохранённым рабочим релизом.
После успеха проверить экран/кнопки и штатное выключение/включение кнопкой;
остальная аппаратная матрица из workflow.md остаётся обязательной для релиза.
