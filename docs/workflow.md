# Разработка командой и критерии готовности

## Один и тот же путь для каждого изменения

1. Issue: симптом, ожидаемое поведение, commit, manifest, boot ID, сценарий
   воспроизведения и обезличенная диагностика. Отдельно отличать отказ SDR,
   OLED, ОС и ложное срабатывание алгоритма.
2. Короткая ветка → изменение → тест, воспроизводящий дефект. Python-ядро
   тестируется на Linux-ноутбуке без Raspberry. Аппаратные зависимости импортирует
   только `ddt/hardware.py`; анализатор CSV не должен знать о GPIO/I²C.
3. `make check replay`; при изменении C также `make build` и
   `DDT_SWEEP="$PWD/build/bin/sweep" make check`. PR-review другим участником.
4. CI: Python 3.12/3.13, C на Ubuntu и Alpine/musl. GitHub Actions конфиг лежит в
   `.github/workflows/check.yml`; на другом Git-хостинге перенести те же команды.
   CI не доказывает работу ARM64, USB, кнопки питания и OLED.
5. Отдельный неизменяемый релиз на стенде из commit SHA + manifest + wheelhouse.
   Выполнить аппаратную приёмку ниже, приложить результаты к PR/релизу.
6. Тег релиза только после приёмки; развернуть с возможностью отката, сохранить
   предыдущий релиз. Не редактировать продакшен-файлы через SSH.

Общий Raspberry-стенд бронируется одним участником на интервал времени: один
владелец запуска SDR. SSH — для установки/логов, не замена Git. Разработчикам
отдельные SSH-ключи; секреты и venv не коммитить. Runtime пока запускается от root
для совместимости с имеющимися правами `/dev`; выделенный пользователь и правила
mdev — отдельное изменение после проверки требуемых доступов на Alpine.

## Матрица аппаратной приёмки

Это предлагаемый минимальный барьер релиза, а не уже выполненные измерения.
Время до первого валидного измерения считать от monotonic uptime/boot ID.

| Сценарий | Повторы | Условие принятия |
| --- | ---: | --- |
| Штатный poweroff, затем снятие/подача питания | 20 | OLED и SDR готовы, без ручного reset |
| Короткая кнопка → завершение ОС → кнопка включения | 30 | Ни одного зависания/пропущенного запуска |
| `rc-service sweep restart` | 30 | Ровно один runtime и один sweep; старые PID исчезли |
| HackRF отсутствует при загрузке, затем подключён | 5 | Явное состояние ожидания; данные появляются автоматически |
| Отключить/подключить USB во время приёма | 5 | Нет старой тревоги при отсутствии данных, приём возобновляется |
| TERM конкретному PID sweep | 5 | Зафиксирован отказ, новый PID и свежие измерения |
| STOP конкретному PID sweep (имитация зависания) | 5 | Таймаут данных, ограниченный stop/KILL, новый приёмник |
| OLED недоступен (отключать провода только без питания) | 3 | Приём продолжается, ошибка видна в логах |
| Непрерывная работа + кнопки порога | 8 часов | Нет утечки процессов/роста RSS и логов без ограничения |

После имитации STOP проверить, что PID остановленного процесса исчез; не оставлять
его в состоянии T. Произвольное отключение питания от работающей SD не включено
в нормальную приёмку — это отдельные разрушительные испытания на резервном образе.
Начальные целевые сроки: готовность от старта runtime ≤20 s при подключённом
исправном SDR; восстановление после переподключения ≤60 s. Уточнять их по замерам,
не скрывать неуспешные повторы увеличением таймаутов.

Для каждого опыта сохранять: commit, конфиг, версии firmware/OS, модель БП/кабеля,
boot ID, способ выключения, время первого измерения, `restarts`, признаки готовности
OLED/GPIO, результат. Снимать APK audit до/после серии. Изменение системных файлов
без обновлений — отдельный блокирующий дефект платформы, не ошибка порога.

## Границы текущего этапа

- Устранена зависимость автозапуска от внешнего FIFO и искусственного рестарта.
  Фактическую надёжность кнопочного выключения подтверждает только матрица выше.
- Тестовые CSV сейчас синтетические. Добавить небольшие реальные записи с метками
  «тишина/помеха/контрольный источник», настройками усиления и антенны. Сначала
  воспроизводить регрессии, затем менять алгоритм/маски, не одновременно.
- Нельзя оценивать качество детектора только отсутствием падений: измерять
  вероятность обнаружения, ложные тревоги/час и задержку на размеченных данных.
- Питание 5V/3A остаётся отдельным риском USB-бюджета. По документации Pi 5 при
  обычном 3A-источнике USB ограничен 600 mA; распознанный 5A даёт 1.6 A:
  [Raspberry Pi power supply](https://www.raspberrypi.com/documentation/computers/raspberry-pi.html#power-supply).
  Не форсировать повышенный ток настройкой EEPROM без проверки источника/кабеля.
- Следующие этапы: зафиксированный образ ОС/APK-зеркало и хеши артефактов,
  аппаратная CI-станция ARM64, отдельный сервисный пользователь, read-only root
  или другой режим защиты SD после анализа режима записи и обновления.
