# DDT: Raspberry Pi 5 + HackRF One

Пассивный пороговый монитор спектра: C-приёмник → Python → SSD1306/I²C и GPIO.
Превышение порога означает **радиочастотную активность, а не подтверждённое наличие дрона**.
Значения мощности не откалиброваны в dBm. Текущие исключённые диапазоны
унаследованы от прототипа; они могут исключать и полезные сигналы.

Обновление уже установленного устройства: `update_ddt <полный commit SHA>` —
отдельная сборка, тесты, проверка готовности и откат при ошибке.
[Установка updater и восстановление](docs/updating.md).

## Быстрый старт разработчика (Linux, Python 3.12+)

Без Raspberry, SDR, OLED и дополнительных Python-пакетов:

```sh
make check
make replay
```

Сборка приёмника на Debian/Ubuntu после установки `build-essential cmake pkg-config
libusb-1.0-0-dev libfftw3-dev`:

```sh
make build
DDT_SWEEP="$PWD/build/bin/sweep" make check
python3 -m ddt --headless --config config/detector.json --status-file build/status.json
```

Остановка: Ctrl+C. Без HackRF приложение показывает `reconnecting` в status.json
и повторяет подключение с ограничением частоты; это не успешный приём.
Для доступа к USB на рабочей машине нужны соответствующие права.
Не запускайте два приложения, использующих один HackRF.

`make build` собирает собственную libhackrf статически, libusb/FFTW остаются
динамическими. Результат: `build/bin/sweep`, **не** `bin/sweep`.
Старый отслеживаемый `bin/sweep` — ARM64-артефакт с привязкой к `/root/ddt/build`;
он оставлен для совместимости, но новый runtime и CI его не используют.

## Что изменено

- Runtime `python -m ddt` сам владеет приёмником; FIFO, отдельный reset prompt
  и обязательный двойной запуск больше не нужны.
- Первый корректный CSV-пакет подтверждает готовность. EOF, завершение C-процесса,
  отсутствие корректных измерений вызывают очистку и повторный запуск.
- Ограниченные очередь, размер строки, задержка повторов и время остановки.
  stderr читается независимо; переполнение отбрасывает самые старые строки.
- OLED/GPIO инициализируются с повторными попытками. Отказ дисплея не считается
  отсутствием радиосигнала. Отображение не содержит трёхсекундного sleep.
- OpenRC supervise-daemon контролирует основной процесс и свежесть его статуса;
  лог имеет ротацию 2 MiB × 4 файла. Таймауты используют monotonic, не NTP.
- C: проверка аргументов/выделения FFT-памяти, построчный stdout, обработка ошибок
  усиления, корректный stop/close, ненулевой код неожиданного прекращения потока,
  обработка только реальной длины USB transfer. Linux посылает sweep SIGTERM
  при смерти родительского процесса.

`scripts/driver.py`, `parser.py`, `ssd1306oled.py`, `reset_hackrf_prompt.py` —
**legacy**, сохранены без изменений для первого отката. Не смешивать их с новым
сервисом. Новые изменения и тесты вносятся в `ddt/`.

## Настройки и диагностика

Образец: [config/detector.json](config/detector.json). Неизвестные ключи и неверные
значения отвергаются. Пути `sweep_binary` разрешаются относительно каталога
запуска; OpenRC устанавливает его в каталог релиза. `serial` позволяет выбрать
один конкретный HackRF; по умолчанию используется первый доступный.

GPIO: BCM 5 — порог +1 dB, BCM 6 — −1 dB; 13 зарезервирован, без действия.
Порог с кнопок действует до перезапуска; постоянное значение задаётся в JSON.
`gpio_chip=0` соответствует предоставленным данным, на другой системе его нужно
сверить. Кнопки опрашиваются через lgpio, с программным debounce 50 ms;
gpiozero и подмена его внутренних методов больше не используются. Очень короткие
нажатия могут не попасть в цикл опроса, удержание не включает автоповтор.

Проверка состояния на Pi:

```sh
rc-service sweep status
.venv/bin/python3 -m ddt status
.venv/bin/python3 -m ddt status --json
cat /run/ddt/status.json
tail -n 100 /var/log/ddt.log
```

`started` у OpenRC и успешный `ddt.health` означают живой цикл управления,
**не** наличие данных SDR. Для рабочего приёма нужны `state=receiving`, рост
`valid_rows`, свежий `last_measurement_monotonic`, а для дисплея — `display_ready`.
`reconnecting` допустим без подключённого SDR, но это деградация устройства.
При превышении пяти аварий основного процесса за 120 секунд супервизор прекращает
повторы: нужно устранить причину и выполнить `rc-service sweep restart`.

Новый статус (schema 2) содержит версию/хеш исходников и бинарника, boot/instance ID,
эффективную конфигурацию с SHA256, накопительные потери очереди, скорости и задержки,
последний отказ и переходы состояний. `ddt status` доступен после установки wrapper
из `deploy/ddt`. Проба `ddt.health --ready` проверяет свежие SDR-данные отдельно от
живости цикла управления; OpenRC продолжает использовать только liveness.
Полный контракт, коды выхода, ограничения оценки покрытия и проверка на Pi:
[диагностика](docs/diagnostics.md).

CSV учитывает реальную ширину бина, а не предполагает 1 MHz. Показывается центр
бина самого сильного подходящего превышения **в строке**; маски применяются к
каждому бину. Это намеренное отличие от старого выбора первого превышения и
проверки только начальной частоты строки. Это не оценка точной частоты несущей
и не поиск максимума по всему проходу спектра. На стенде сравните результаты
на одних и тех же записях перед принятием нового поведения.

Изменения не исправляют повреждение SD/ОЗУ, недостаточное питание и зависание
ядра/USB, требующее аппаратного сброса. Автоматического USB power-cycle,
прошивки EEPROM/HackRF или перезагрузки всей Pi здесь намеренно нет.
Установка OpenRC и испытания на реальном ARM64/I²C/USB обязательны перед релизом.
